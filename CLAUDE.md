# Lottie Theme Studio — orientation

**What this is.** A tool that turns a dark-theme Lottie animation into a light one (or
back) without After Effects: the colours are found, identified visually, mapped, and
written back. It exists because the source file is usually gone, the exporter scattered
colour across eight different shapes of JSON, and "invert the lightness" produces washed-out
grey and dark halos on a white page.

**What the work usually is.** Someone hands you an animation and a target — a screenshot
of the page it has to sit on, or just "make a light version". You produce the recoloured
JSON and you *look at it* before saying it is done.

## The one architectural rule

```
packages/core   @lottie-theme/core — all the logic, zero UI or filesystem dependencies
packages/cli    lottie-theme — the same logic on the command line
packages/mcp    lottie-theme-mcp — the same logic as tools for an AI agent
packages/sync   lottie-theme-sync — dev-only live bridge between the editor and an agent
apps/web        the editor (Next.js, Tailwind, shadcn/ui, Zustand, lottie-web)
```

`core` is the only place that knows how a colour is found or changed. The other three are
thin shells. **Never reimplement core logic in a shell** — an animation edited by hand and
one edited by a script have to come out identical, or neither can be trusted.

Two consequences worth knowing before you edit:
- `core` must stay free of `node:fs` and of anything browser-only. It is bundled into the
  page as TypeScript source.
- Imports carry explicit `.ts` extensions. Bare specifiers do not resolve in Node, `.js`
  does not resolve in webpack when the package is consumed as source; `./types.ts` suits
  Node, webpack and vitest at once.
- `erasableSyntaxOnly` is on everywhere. Node runs these files by stripping types, so
  syntax that must be *compiled* (parameter properties, enums) is a build error by design.

## Running it

```bash
pnpm install
pnpm dev          # the editor on http://localhost:3000
pnpm sync         # optional: live bridge, so an agent and the editor share a session
pnpm test         # core + sync unit tests (290 + 12)
pnpm typecheck    # every package
pnpm smoke        # 43 headless browser checks; needs `pnpm dev` running
```

`pnpm smoke` is the one that catches what unit tests cannot: that lottie-web mounts an SVG,
that an edit reaches the rendered output, that undo restores it, that the console is clean.
Everything it drives is addressed by `data-testid` or `[data-section]`, so restyling does
not break it — keep it that way. It needs animations on disk; with none it fails on the
first check rather than skipping, which reads as a regression and is not one.

## The workspace root

Working on a folder rather than one file goes through a single root that four things share:
the dev server's file list, the sync hub, the MCP server, and the CLI. `LOTTIE_WORKSPACE`
sets it (default: this repository), `LOTTIE_DIRS` picks the folders inside it to browse
(default: `lotties,lotties-light`), and `apps/web/.env.example` documents both.

There is one root **because a file's identity is its path relative to it**. The browser
sends the open file's id to the hub as a path and the hub resolves it against its own root;
two roots that disagree is two tools editing different files while reporting success. Any
new surface that names a file has to use the same root and the same relative paths.

The corpus in `lotties/` is gitignored — bring your own animations, or point `LOTTIE_DIRS`
elsewhere. Tests that walk it skip themselves when it is absent, so a fresh clone is green.
`examples/` holds reproducible before/after pairs generated by the CLI and the MCP renderer,
not screenshots taken by hand.

## Recolouring an animation

The MCP server is wired up in `.mcp.json`, so the tools are there when Claude Code opens
this folder — `read_palette`, `layer_tree`, `suggest_theme`, `render_preview`, `apply_edits`,
`sample_screenshot`, plus `session_state` and `push_edits` when the live bridge is running.
It runs the TypeScript source directly, which needs **Node 22.18+ or 24**.

Load the **`lottie-theming` skill** before doing any actual recolouring work. It carries
the workflow and the traps — gradients that fade into the backdrop, values shared through a
reused precomp, embedded bitmaps — that decide whether the result is right or merely
different.

## Where the reasoning lives

- `README.md` — what this is, how to run it, the CLI and the MCP tools, and the list of
  things deliberately not done yet.
- The `/docs` page in the app — how Lottie actually stores colour, in eight shapes.
- The code itself. Comments here explain *why*, and the surprising ones carry the reason
  they are surprising — a probe built from the edited document rather than the original,
  effect colours addressed by path rather than by slot index, a corpus test that skips
  instead of failing. Read the comment before changing the line.

When a piece of work turns up something that was not true — a trap, a format quirk, a
failure that only shows on the page — write it into the comment beside the code that now
handles it, or into the skill if it changes how the job is done.

## House style

Comments explain *why*, never *what* — the code already says what. Prose in docs and
commit messages is plain and specific: no marketing adjectives, no "comprehensive", no
emoji. Match the density and idiom of the file you are editing.

**Do not commit.** Leave finished work in the working tree — the owner reviews it and
commits himself. If you are explicitly asked for a commit: a `feat:`/`fix:` prefix, one
short line, no essay of a body, and no `Co-Authored-By` or session trailer.
